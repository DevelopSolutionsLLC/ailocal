# Architecture

## Purpose

AGENTS.md owns the repository map, the ownership rules and the engineering invariants; `ailocal help` owns the command list. This document answers only what none of those can: how a request moves through the running system.

ailocal runs AI coding clients against local models on Apple Silicon. Ollama serves the models on the host GPU; LiteLLM fronts them on `127.0.0.1:4000` as an OpenAI- and Anthropic-compatible proxy that exposes **capabilities** (`architecture`, `implementation`, `review`, `fast`, `completion`) rather than model tags. A hardware profile decides which model answers each capability, and every client configuration is generated from that one decision.

---

## Runtime flow

```
authored profiles + client policy + templates
                    ↓
              policy.py                one reader, fails closed
                    ↓
             generation                the only generator
                    ↓
      one staged generation transaction
        stage → validate → back up → replace → roll back on failure
                    ↓
             $AILOCAL_STATE            outside the checkout
                    ↓
      Compose mounts        client deployment
                    ↓                     ↓
      LiteLLM · SearXNG      Claude · Codex · VS Code
```

## Runtime state

Every generated file is written straight into the home its consumer reads it from. There is no staging tree and no deploy-time copy. Each file carries a `Generated by ailocal. Do not edit.` header naming its source.

```
$AILOCAL_STATE/                 what LiteLLM mounts, plus the marker (inherits umask)
├── active-profile              selected tier
├── litellm-config.sha          restart fingerprint
├── litellm/                    ── bind-mounted into the container ──
│   ├── config.yaml             proxy configuration
│   └── capabilities.json       capability → backend, context (read by the hooks)
├── searxng/
│   └── settings.yml            rendered; may carry the GitHub search token, mode 0600
├── env                         GENERATED. the master key and SearXNG secret, mode 0600
├── agents/preload.sh           the login LaunchAgent's program
└── captures/                   writable by the proxy; opt-in payload capture

~/.config/ailocal/              ── authored policy AND generated client config, mode 0700 ──
├── profiles/                   AUTHORED. yours to edit; ailocal preserves edits
├── .env.local                  YOURS. provider keys and overrides, mode 0600
├── integration-contract.json   published facts for external consumers
├── configure.zsh               shell integration
├── claude/settings.json
└── codex/config.toml, model_catalog.json
```

Deleting either root and re-running `ailocal start` recovers everything generated. Deleting `profiles/` or `.env.local` does not: those are yours.

The environment has exactly two owners and one precedence — generated state, then your overrides:

```
~/.local/state/ailocal/env    ailocal's, generated    LITELLM_MASTER_KEY, SEARXNG_SECRET
        +
~/.config/ailocal/.env.local  yours                   provider keys, overrides — WINS
        =
effective environment         loaded in that order by every consumer
```

`ailocal install` migrates a legacy combined `~/.config/ailocal/.env` automatically, keeping the generated secrets byte-for-byte. No key is ever rotated.

## What an install actually writes

The complete on-disk footprint of `ailocal install` and the optional `ailocal clients` step. Nothing outside this list is created. Shipped `deploy/` and `clients/` trees are read in place from the installed package and never copied elsewhere.

**Policy root — `~/.config/ailocal` (`$AILOCAL_CONFIG`)**

| Path | Written by | Notes |
|---|---|---|
| `profiles/*.toml`, `profiles/clients.toml` | `install` | The only thing `provision()` copies. Replaced only when the file still matches the digest recorded at install time; anything you edited is preserved, anything you deleted stays deleted, anything no longer shipped is retired. |
| `.env.local` | `install` | Created empty if absent, then **never written again**. Your provider keys and any override of a code default. Mode 0600. |

**State root — `~/.local/state/ailocal` (`$AILOCAL_STATE`)**

| Path | Written by | Notes |
|---|---|---|
| `env` | `install` | Generated `LITELLM_MASTER_KEY` and `SEARXNG_SECRET`, mode 0600. Regenerated only when absent — never on upgrade, because the key is embedded in every generated client config. |
| `install-manifest.json` | `install` | Digests of what was *shipped* (never of what is on disk) — the provenance that makes edit-preserving upgrades possible. |
| `active-profile` | `install` | The selected tier; the sole writer is `select_tier()`. |
| `litellm/config.yaml`, `litellm/capabilities.json` | `generation` | Bind-mounted into the proxy container. |
| `litellm-config.sha` | `runtime` | Restart fingerprint. *(start path)* |
| `searxng/settings.yml` | `runtime` | Rendered from the shipped template; may carry the GitHub search token, parent dir 0700. *(start path)* |
| `agents/preload.sh` | `install` | Program for the preload LaunchAgent. Resolves the model tag at run time so it can never warm a stale one. *(launchd path)* |

The config root inherits the umask; the state root is `0700`, set when the generated environment is written, because it holds the master key. Secrets are protected per file as well (`env`, `.env.local` at 0600) and by the deployed-client root's own 0700, not by the state root.

**Generated client config — `~/.config/ailocal` (`$AILOCAL_CLIENTS`)**

Same directory as the policy root by default, different owner and lifecycle: this is disposable and rewritten on every start.

- `integration-contract.json` — the machine-readable seam external tooling reads
- `configure.zsh` (generated), `finalize.zsh`, `scratchpad-hook.sh`, `compact-hook.sh` (copied, 0755)
- `claude/` — `settings.json`, `.claude.json` (seeded only if absent), and `agents/`, `commands/`, `references/` installed as *managed* directories (each carrying a `.ailocal-managed` manifest): a marker-delimited block appended by another tool is carried across the overwrite, and a symlink is never written through
- `claude/plugins/` and `claude/backups/` — created inside this root by the `claude` binary that `lsp_baseline()` invokes, not by ailocal. Registering the marketplace clones `anthropics/claude-plugins-official` here, and the CLI rewrites the seeded `.claude.json`, keeping a timestamped backup. Not everything under this root is ailocal-generated.
- `codex/` — `config.toml`, `model_catalog.json`, `skills/local-research/`. No `AGENTS.md`: like the claude root, this root carries no instruction policy, because Cadence composes that path; an `AGENTS.md` that is byte-identical to one ailocal wrote earlier is retired, and any other is left alone. The catalog carries each capability's admitted window; selecting a model needs no generated launch preset.

Codex's `config.toml` is co-owned: regeneration preserves native trust records, its screen-reader detection flag, and MCP server tables outside the template's server names. The template always owns ailocal's research server; external registrars retain ownership of their own server and nested settings.

**Host state outside both roots**

| Path | Written by | Notes |
|---|---|---|
| `~/Library/LaunchAgents/com.ailocal.{ollama,ollama-env,preload}.plist` | `install` | Bootstrapped into the GUI domain. `ailocal teardown` removes them. *(launchd path)* |
| `~/Library/Logs/ailocal/*.log` | launchd | stdout/stderr of the agents above. *(launchd path)* |
| `/Users/Shared/ollama/models` | `install` | Shared model store, group-writable + setgid. Existing `~/.ollama/models` is *moved* here (rename, one file at a time) before `OLLAMA_MODELS` is repointed. *(launchd path)* |
| `~/.zshrc` | `clients` | Exactly two marker-commented lines (`# ailocal-configure` first, `# ailocal-finalize` last), inserted idempotently after a timestamped backup. |
| `~/.copilot/instructions/ailocal.instructions.md` | `clients vscode` | The one Copilot instruction file: local-stack facts, terminal protocol, and the shared build checklist appended. |
| VS Code `User/mcp.json` | `clients vscode` | Registers `research` through VS Code's native `--add-mcp`, with the absolute launcher path because a Dock-launched VS Code has a minimal `PATH`. Other servers are preserved and a foreign `research` entry is left untouched. |
| VS Code `User/chatLanguageModels.json`, `User/settings.json` | `clients vscode`, `start` | `clients vscode` writes the native `customendpoint` group named `ailocal` (explicit aliases, limits, thinking and sampling from the active profile; FIM excluded), replacing a retired `litellm-connector` group only when it targets this proxy, and prunes deprecated/harmful settings. `start` refreshes an already configured group and the marked model-guidance block of the Copilot instruction file; it never creates a provider, and an unparseable editor file is reported and preserved rather than blocking the stack. The API **key** is not written: it lives in VS Code SecretStorage, which no supported interface lets ailocal touch — that one step stays manual. |

`~/.zshrc` is created if absent and backed up (`.zshrc.bak.<timestamp>`, newest 3 kept) before either line is inserted.

Hosted roots receive only public documentation MCP registrations through the native Claude/Codex CLIs. The bundled delegation server is registered as `agent` in the isolated roots only; hosted delegation is Cadence's `local-agent` declaration, which carries an owner marker its uninstall can prove. The names differ because Cadence drops a declared name from every client it is not scoped to — the same split as `research` and `local-research`. The shipped endpoint list lives in `resources/clients/documentation.toml`, read by `policy.py`; install and client setup share the same idempotent provisioner. Foreign registrations and other client settings are preserved, and registration failures return a nonzero status. Hosted registrations remain after teardown. Isolated roots are reached through `CLAUDE_CONFIG_DIR` / `CODEX_HOME` in the wrappers. `lsp_baseline()` enables the official LSP plugin for each language server already present (Python, TypeScript, Go, C/C++) in the isolated root **only**. Plugin state is per config root.

**Uninstalling:** `ailocal teardown` (containers + LaunchAgents), delete the two roots, remove the two `~/.zshrc` lines, and optionally `/Users/Shared/ollama/models`. The LSP plugins live in the isolated root and go with it.

## Containers

**LiteLLM**

| Mount | Kind | Why |
|---|---|---|
| `<package>/resources/deploy/litellm → /app/config:ro` | shipped | hooks, capability registry, config template — mounted from the installed package, never a copy |
| `$AILOCAL_STATE/litellm → /app/generated:ro` | generated | the config the proxy actually loads |
| `$AILOCAL_STATE/captures → /app/captures` | writable | the only path the proxy may write |

Shipped assets are mounted read-only from the installed package. Generation completes before `docker compose up`; nothing regenerates a mounted asset while the stack runs.

The proxy starts with `--config /app/generated/config.yaml`. Callback modules are named by absolute path because LiteLLM resolves them relative to the config file, which lives on a different mount from the hooks.

Profiles and client templates are not visible to the container.

**SearXNG**

| Mount | Kind | Why |
|---|---|---|
| `$AILOCAL_SEARXNG_SETTINGS → /etc/searxng/settings.yml:ro` | generated | may carry the GitHub search token; rendered outside the checkout so committing it is impossible |
| `<package>/resources/deploy/searxng/limiter.toml → /etc/searxng/limiter.toml:ro` | shipped | bot-detection policy |

Ollama runs on the host, not in a container, and is reached at `OLLAMA_HOST`.

## Data flow

```
profiles/<tier>.toml     capability → model, geometry
profiles/clients.toml             client surface → capability
                    ↓
policy.py           resolve_role · geometry · load_client_policy · required_models
                    ↓
generation          model_list · aliases · capabilities · client configs · contract
                    ↓
$AILOCAL_STATE      one root, one writer
                    ↓
LiteLLM             capability alias → Ollama model; tool schemas filtered
                    before the backend sees them
                    ↓
deployment          ~/.config/ailocal/<client>/ — clients read the deployed copy,
                    never the checkout or the generated staging area
```

External consumers read the deployed `integration-contract.json` from the client config root — never the repository. Schema 3 adds `instructions.<client>.max_bytes`, the largest instruction file each client root should carry; a co-installed composer (Cadence) fits it, and `ailocal check` warns about any file over it whoever wrote it. ailocal writes no `CLAUDE.md` or `AGENTS.md` and works without one; see [ADR 017](adr/017-instruction-budget.md).

## Geometry

The one rule every profile follows: **admission is bounded by memory, up to the backend's native window; compaction is the client's latency budget, never a geometry input.** Each profile carries its budgets and links the evidence and remaining hardware limits.

- The native window caps everything. Every shipped chat backend reports 262144 tokens (`max_position_embeddings`, `ollama show`), so no role totals more.
- The operator chooses the admitted window within the native limit and available memory. Architecture retains the original live totals of 106496 / 139264 / 196608 / 262144 tokens for 16/32/64/128 GB; Cyber uses the same total per tier, with its own output reserve. Aliases sharing one primary backend use the same total. Shipped chat defaults use GGUF MTP with eager context allocation and q8_0 KV; targets, draft heads, projectors, runtime buffers, macOS and Docker all consume memory. Historical MLX figures do not establish this working set. Earlier native-maximum probes loaded individually on the 64 GB host; physical 16/32/128 GB fit and simultaneous filled-window residency remain unverified. See the [native model audit](model-audit.md#installed-clients-cache-and-memory).
- Roles that share a backend share its window and differ only in output reserve: `context_input = total − max_output`.
- Shipped Cyber budgets follow the primary's window; edited operator budgets can differ. Cyber is a separate model, so residency must include both backends rather than assuming two full windows fit. Ollama can evict an idle model when another loads, and Cyber's shorter `keep_alive` releases it sooner. The current 64 GB native trial observed automatic fast-model eviction and zero swap.
- Cold prefill grows with depth. The historical 64 GB measurement of 231,390 tokens in 561 seconds was on MLX and does not transfer to the new GGUF targets. Clients bound conversation latency through their own compaction; the declared window remains an admission budget, not a cold-prefill performance guarantee.

## Context and compaction: who owns what

**ailocal owns the numbers, not the conversation.** It stores no conversation history, never summarises, and never rewrites a client's history. Delegation stores private session identity and permission bindings under the state root, without prompts, replies or transcripts; native clients own their history. A resume inherits the recorded worker, mode, model and working directory, rejects conflicting options or changed execution policy, and rechecks the current operator ceiling. Unmanaged sessions must start fresh. [ADR 015](adr/015-delegation-inputs-and-resume.md) records that contract and explicit image attachment delivery. It owns geometry — `policy.geometry()` derives `total_context` (Ollama `num_ctx`), `num_predict`, and `max_input_tokens = context_input` from each profile — and declares to each client the window LiteLLM admits.

**The clients compact, at their own default points.** ailocal sets no trigger; each client computes one from the window it is given, and that point lies below admission:

| Client | ailocal declares | Client default | Source |
|---|---|---|---|
| Claude Code | `CLAUDE_CODE_MAX_CONTEXT_TOKENS = context_input` of the launch default, `CLAUDE_CODE_MAX_OUTPUT_TOKENS = max_output` | compacts at window − min(max output, 20000) − 13000 | [REAL] Claude Code 2.1.310 binary |
| Codex | `context_window = max_context_window = context_input` per catalog entry | compacts at 90% of `context_window` when `auto_compact_token_limit` is unset | [REAL] Codex 0.163.0 source |
| VS Code Copilot Chat | LiteLLM's `max_input_tokens`, read by the LiteLLM provider | summarises at a fraction of `maxInputTokens` with no setting | [REAL] Copilot Chat 0.71.0 bundle |

`CLAUDE_CODE_MAX_CONTEXT_TOKENS` declares admission rather than the total window because Claude Code reserves at most 20000 tokens for output: declaring the total on a 262144-token tier with 32768 of output would leave its trigger 232 tokens under admission. Declaring `context_input` keeps at least 13000 + min(max_output, 20000) tokens of margin on every tier. The `PreCompact`/`PostCompact` hooks only record that compaction happened, in `$AILOCAL_STATE/compaction.jsonl`.

A `[compaction]` section in an installed profile is retired and ignored, like `[embeddings]`; regeneration removes `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` from an existing `settings.json`.

Claude Code's variables are process-wide while its model slots route to different capabilities. They describe the launch-default role; `settings.json` lists the background slots whose smaller limits they cannot express.

**One picker, one description.** Claude Code's `/model` is the generated [`modelPicker`](https://code.claude.com/docs/en/settings-reference#modelpicker) with `replaceBuiltInOptions: true`: every enabled capability once, in `policy.ROLES` order, and nothing else besides Default and the current session's model. Gateway discovery is not enabled, because that picker hides it. Before this the picker kept the built-in lineup on top and, with gateway discovery on, listed `ailocal-cyber` twice further down (operator report, 2026-10-26, Claude Code 2.1.310). The `ANTHROPIC_DEFAULT_*_MODEL` slots still route background work and subagents. `policy.capability_description()` renders `<role> — <model name>, <N>K ctx` for the picker, the Codex catalog and the LiteLLM config, from the role text and the model guide's `name`. VS Code's LiteLLM provider shows the model id and its token limits and has no free-text description field.

**The engines enforce context, and they do not agree.** The MLX runner applies context per request; llama.cpp fixes it at load and truncates an over-long prompt from the front with HTTP 200 and no error. LiteLLM's `max_input_tokens` is the only layer that fails loudly. Engine behaviour is recorded in `resources/deploy/litellm/registry.yaml`.

## Extension points

**Add a model** — edit the capability's `active` in `profiles/<tier>.toml`, then `ailocal install`.

**Add a profile** — create `profiles/<tier>.toml` and add the tier to `policy.TIERS`. Selection thresholds live in `src/ailocal/install.py`.

**Add a capability** — add the role to the profiles and to `policy.ROLES`, then map client surfaces to it in `profiles/clients.toml`.

**Add a client template** — place the authored template under `resources/clients/<client>/`, emit its rendered output to `$AILOCAL_STATE/clients/<client>/` from the generator, and deploy it from `src/ailocal/clients.py`. Never write generated output beside the template.

**Add a bundled integration** — place it under `resources/integrations/<name>/` with its own
provenance and licences, provision it from `src/ailocal/clients.py` into the state root, and
give it a check in `src/ailocal/checks/`. It runs as a subprocess with its own interpreter, so
ailocal's `dependencies = []` is unaffected. See the artifact component and ADR 011.

## The claude-local surface

Inference is **always** through LiteLLM. There is no direct-Ollama path for an agent or a
subagent, in production or otherwise; the proxy is the only route, which is what makes the
gateway, the registry and the metrics meaningful.

Client configuration shapes what the model sees on a `claude-local` request, without writing to `~/.claude`:

- **MCP tool search** (`ENABLE_TOOL_SEARCH=true`) defers what can be deferred. Requires
  LiteLLM ≥ 1.98, which preserves the mid-array `role: "system"` messages the deferred-tool
  listing travels in.
- **Native Workflow disabled**, because its schema cannot be deferred at all.
- **The bundled artifact MCP**, which declares `alwaysLoad` and is therefore eager.
- **The bundled research search tool**, which also declares `alwaysLoad`; local answer synthesis is opt-in.

A delegated subagent gets what it declares minus `Grep`/`Glob`; the matrix and measurement method are in [claude-local.md](claude-local.md#known-subagent-limitations). Adding research changes the parent tool surface; an exact current tool/byte count has not been measured.

**Cadence is optional and separately owned.** ailocal neither installs nor depends on it, and
`claude-local` is complete without it.

## Local research

The bundled `resources/integrations/local-research/` subprocess uses the official MCP SDK in its own state-root venv, following ADR 011. `ailocal mcp research` supplies configuration through existing policy and environment readers; the component imports no ailocal code. Provisioning uses Claude Code's native `mcp add-json` command with `CLAUDE_CONFIG_DIR` set to claude-local's owned root, preserves other servers, and refuses a foreign registration collision. The generated codex-local template registers the same launcher and receives the same routing skill. VS Code registers it in the user `mcp.json`, which hosted Copilot models share because VS Code has no separate local root. [REAL] Codex 0.163.0 completed `research.search` through the local proxy on 2026-10-18, replacing the earlier version's restriction for this server. Hosted clients remain Cadence's responsibility.

Search plans a bounded set of SearXNG requests per preset, filters by engine attribution and DNS site scope, merges duplicates across providers, and reports coverage, attempts, fallbacks and provider failures. Brave is called directly, only from here, behind a cross-process ledger (`brave-ledger.sqlite3`) that reserves each request before sending it. Optional synthesis uses `ailocal-fast` through LiteLLM with no tools, no conversation history and no hosted fallback. It is disabled in the normal claude-local registration because of the shared inference slot. [ADR 014](adr/014-local-research.md) records this evidence and inference boundary.

Public-page fetching checks all resolved addresses and redirects, pins connections to validated public addresses, verifies TLS hostnames, refuses credentials in URLs, and ignores ambient proxy settings. Only HTML/plain text is read, with no browser, subresources or login bypass. Limits are 10 search results, 4 fetched pages, 1 MiB per response, 8,000 extracted characters per page, 24,000 evidence characters, 800 output tokens and 120 seconds per tool call; the launcher lowers input/output budgets to fit the selected role. Character accounting is approximate; the proxy enforces its actual token window. Failures remain visible as source provenance or MCP tool errors. Cancellation closes pending network work.

SQLite caches search responses for 15 minutes and page text for 30 minutes under `$AILOCAL_STATE/local-research/`, with a 64 MiB cap and bounded entry count. Cache keys include endpoint, scope and engine policy; credentials, conversations and synthesized answers are not stored. Cache failures produce visible warnings. Source IDs are checked before an answer is returned; that check does not establish factual support. `tests/research.py` covers contracts with staged backends and real MCP transport. `tests/measure_research.py` performs opt-in live measurement separately from the deterministic gate.

## Mermaid validation

Invalid Mermaid can no longer be published: `publish()` parses every diagram with the real Mermaid grammar (`mermaid_validate.py`, headless Chrome over `vendor/mermaid.min.js`, ~1.7 s per diagram) and returns the parser error to the MODEL instead of serving a bomb icon to the human. The verdict has THREE states and the third is the point -- VALID publishes, INVALID is refused with the parser message, and UNAVAILABLE (no browser, launch failure, timeout, no verdict) is ALSO refused, because reporting an unchecked diagram as a successful publish is the original defect. Only the Mermaid path is gated: `html`, `architecture` and Markdown with no fence never start a validator and cost nothing. Chrome runs in a throwaway `--user-data-dir` and is killed once the verdict is read; it never touches the profile a person is using.

`test_mermaid_validate.py` (CORE) asserts the state machine with the browser replaced through the `runner` seam, plus one bounded real parse; `test_mermaid_grammar.py` (FULL) is the authoritative corpus and launches a browser per fixture.
